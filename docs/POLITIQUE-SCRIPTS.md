# Politique des scripts, du panneau de boutons et de la publication

## 1. Objet

Ce document consigne les décisions prises avec l'utilisateur sur trois sujets qui structurent la suite du plugin : un panneau de boutons à droite de la zone de rédaction, un mécanisme de scripts qui permet d'ajouter des fonctions sans les charger toutes, et la publication du plugin dans le répertoire communautaire d'Obsidian. Il complète docs/POLITIQUE-EXPORT.md, qui reste la référence pour le moteur d'export. Les règles de travail de la section 4.1 de ce document s'appliquent ici aussi : questions par petits groupes avec une recommandation, explications pas à pas pour toute manipulation sur GitHub, aucune dépendance ajoutée sans accord, aucun test désactivé.

Le plugin s'appelle Bigorneau, son identifiant est bigorneau et son auteur est Olivier Holweck. Il s'appelait Mindmap Note Writing jusqu'à la version 0.1.7. Le dépôt GitHub est renommé comme le plugin.

## 2. Le panneau de boutons

L'utilisateur souhaite un panneau de petits boutons placé à droite de la zone de rédaction, au milieu de la hauteur de la page, disposés de haut en bas, dans tous les éditeurs de notes. Un réglage permet de l'afficher ou de le masquer, et une commande le bascule. Chaque fonction ajoutée au plugin reçoit un bouton et, en même temps, une commande de la palette de commandes, ce qui permet de lui attribuer un raccourci dans les réglages d'Obsidian. Le premier bouton porte l'icône du bigorneau, symbole du programme que l'utilisateur dessinera plus tard (une icône standard d'Obsidian la remplace en attendant). Il sert uniquement aux scripts : il ouvre la fenêtre des scripts. Un bouton d'aide se trouve juste en dessous et ouvre une fenêtre d'aide avec une zone de recherche qui fonctionne hors connexion, dans des textes fournis par le plugin et par chaque script, en français ou en anglais selon la langue du plugin. Les autres boutons sont ceux des fonctions ajoutées, dans l'ordre d'ajout. L'utilisateur les déplace vers le haut ou vers le bas par un clic long suivi d'un glissement. Une liste dans les réglages permet aussi de masquer un bouton (la fonction reste dans la palette de commandes) et de réordonner les boutons sans les faire glisser.

Pour réaliser cela, le plugin gardera un registre de fonctions. Une fonction est décrite par un identifiant, un nom en français et en anglais, une icône, une action et un texte d'aide. Le panneau et la palette de commandes lisent ce registre, et les scripts y enregistreront leurs fonctions. Les cinq commandes d'insertion de la version 0.1.7 (note de bas de page, table des matières, légende de tableau, formule en ligne, formule en bloc) en seront les premières entrées. Le panneau est livré dans la version 0.1.9, avec le registre de fonctions, le bouton d'aide et la fenêtre d'aide (entrées d'aide en français et en anglais, recherche hors connexion, enregistrement d'entrées par les futurs scripts). Le bouton bigorneau n'y figure pas encore : il n'aurait rien à ouvrir tant que le mécanisme de scripts n'existe pas, et il arrive avec la version 0.2.0. Il est masqué par défaut sur tablette et téléphone, faute de place, et un réglage l'affiche. Une fonction qui écrit dans la note n'agit qu'en mode édition. Le glissement se fait par clic long, sans déplacer le bouton dans la page pendant le geste (le déplacer ferait perdre la capture du pointeur), et il a été vérifié dans Chromium avec de vrais événements de pointeur.

## 3. Les scripts

Un script est un module qui ajoute des fonctions au plugin : il enregistre une fonction (donc un bouton et une commande), lit la note active, ajoute une langue, une police ou un style d'export. Un script peut en exiger un autre : le script Document long utilisera le script Formules pour dessiner les formules, et laissera sinon le texte tel qu'il est écrit. Chaque script déclare son nom et sa description en français et en anglais, la version de l'interface pour laquelle il est écrit et les scripts dont il dépend. Le plugin refuse proprement un script dont la version d'interface est incompatible.

Les politiques du répertoire communautaire interdisent à un plugin de s'installer ou de mettre à jour lui-même ou ses dépendances. Un catalogue qui télécharge des scripts depuis GitHub n'est donc pas retenu. L'utilisateur a choisi que les scripts officiels soient intégrés au plugin et s'activent ou se désactivent dans la fenêtre du bouton bigorneau, sans aucun téléchargement. Un script désactivé ne s'exécute pas : il n'enregistre ni commande ni bouton, et ses bibliothèques ne sont pas initialisées (MathJax, par exemple, ne se charge qu'à la première formule). Le fichier du plugin reste de la taille actuelle, environ 3,4 Mo. Les scripts personnels ou de tiers s'ajoutent à la main avec un bouton « Ajouter un fichier de script » qui ouvre un sélecteur de fichier. Le plugin copie le fichier choisi dans son dossier technique, invisible dans Obsidian. Comme le fichier peut venir de l'extérieur du coffre, le README le déclare.

Au premier lancement d'un script ajouté à la main, le plugin demande une confirmation en montrant le nom, l'origine et la description du script, et mémorise la réponse. Un script dont l'empreinte a changé depuis la confirmation fait redemander l'accord. Un script a les mêmes pouvoirs que le plugin, c'est-à-dire qu'il peut lire et modifier toutes les notes et, sur ordinateur, accéder aux fichiers de la machine. La confirmation sert à ce que l'utilisateur le sache avant d'accepter.

Obsidian ne permet pas de retirer proprement une commande en cours d'usage. Quand l'utilisateur désactive un script, le plugin affiche donc un message qui précise que la désactivation ne prendra effet qu'au redémarrage d'Obsidian.

L'export actuel reste dans le plugin tant que le mécanisme de scripts n'est pas éprouvé. Il sera ensuite déplacé tel quel dans le script Document long, appelé Long document composer en anglais, avec le même résultat et les mêmes tests, dans une version dédiée. Sans l'activation de ce script, les entrées d'export du menu proposeront de l'activer. Les gabarits de documents (rapport, mémoire, ouvrage), prévus comme deuxième partie de la phase 7, deviendront des scripts de styles. Les scripts envisagés par l'utilisateur sont les suivants : Document long, qui donne accès aux autres ; la typographie française, la typographie anglaise britannique et la typographie anglaise américaine, chacune avec ses règles ; des polices et des styles d'export supplémentaires ; une sortie HTML ; Formules, pour composer facilement des formules complexes ; un script pour dessiner les tableaux plus facilement ; un script pour nommer les figures, les images et les tableaux. Ils seront réalisés l'un après l'autre, en TypeScript dans ce dépôt, testés sans Obsidian comme le reste du moteur.

## 4. Publication dans le répertoire communautaire d'Obsidian

L'utilisateur souhaite publier le plugin prochainement. La procédure ci-dessous est tirée de la documentation officielle des développeurs (pages Submit your plugin et Plugin guidelines du dépôt obsidianmd/obsidian-developer-docs) et des pages Developer policies et Submission requirements for plugins, que l'utilisateur a copiées dans la conversation le 2 octobre 2026.

Le dépôt doit contenir à sa racine un fichier README.md qui décrit le but du plugin et son usage, un fichier LICENSE et un fichier manifest.json. Il faut ensuite créer sur GitHub une release dont l'étiquette est identique à la version du manifest (trois nombres séparés par des points) et y joindre main.js, manifest.json et styles.css. La soumission se fait sur le site community.obsidian.md : connexion avec un compte Obsidian, liaison du compte GitHub pour prouver que le dépôt appartient au soumissionnaire, puis ajout du plugin. Le répertoire lit le manifest.json à la tête de la branche principale, et l'identifiant du plugin doit être unique et ne pas contenir le mot obsidian. Une revue automatique indique ce qui est à corriger ; les corrections se font dans le dépôt, avec une nouvelle release à la version augmentée. Après publication, l'annonce se fait dans le forum Share & showcase et sur le canal #updates du Discord.

Les politiques interdisent le code obscurci, les annonces dynamiques, la télémétrie côté client et l'installation ou la mise à jour par le plugin lui-même de ses dépendances. Elles demandent de déclarer dans le README l'usage du réseau, l'accès à des fichiers hors du coffre, tout paiement ou compte requis, et de respecter les licences du code utilisé, avec les attributions dans le README. Elles interdisent de faire croire à un plugin d'Obsidian. Les exigences de soumission demandent une description de 250 caractères au plus, qui commence par une phrase d'action, se termine par un point et ne contient ni émoji ni caractère spécial, l'indicateur « ordinateur seulement » si le code utilise Node.js ou Electron, des identifiants de commande qui ne contiennent pas l'identifiant du plugin, et l'absence de code d'exemple. Les consignes de revue demandent de ne pas utiliser innerHTML, de ne pas mettre de raccourci clavier par défaut, de limiter les styles écrits dans le code, d'écrire les textes de l'interface avec une majuscule initiale seulement et de ne pas mettre de titre au premier groupe de réglages.

La version 0.1.8 met le dépôt en conformité : licence MIT au nom d'Olivier Holweck, README en anglais et en français avec les déclarations et les crédits des licences, description du manifest en anglais, renommage en Bigorneau avec reprise des réglages de l'ancien plugin, remplacement des dix expressions régulières avec « lookbehind » (à ma connaissance, les iPhone et iPad antérieurs à iOS 16.4 ne les acceptent pas et le plugin entier ne se chargerait pas sur ces appareils), remplacement des seize usages de innerHTML par la construction d'éléments SVG, et retrait du titre du premier groupe de réglages de l'export. Un test automatique (tests/publication.test.ts) vérifie ces points à chaque modification. Il reste 120 affectations de styles en ligne environ dans le code : ce sont des positions et des tailles calculées, des couleurs choisies par l'utilisateur et des affichages ou masquages d'éléments, qui ne peuvent pas être écrits à l'avance dans la feuille de style. Ceux qui fixaient des polices dans l'aperçu de l'export sont passés dans styles.css. Le reste sera revu selon les retours de la revue automatique. Le plugin n'utilise aucun accès au réseau, ce que le README déclare.

Un contrôle dans l'ancienne liste publique des plugins (8302 entrées, consultée le 2 octobre 2026) montre qu'aucun plugin ne s'appelle Bigorneau, que l'identifiant bigorneau n'est pas pris et qu'aucun nom de plugin ne contient le mot Obsidian. Cette liste n'est peut-être pas identique à celle du nouveau répertoire : le contrôle est à refaire au moment de la soumission. L'identifiant du plugin est définitif une fois publié.

## 5. Ordre des travaux

La version 0.1.8 prépare la publication. La version 0.1.9 apporte le panneau de boutons, le registre de fonctions et l'aide. La version 0.2.0 apporte le mécanisme de scripts. Viennent ensuite le déplacement de l'export dans le script Document long, puis les autres scripts un par un, puis la phase 8 de comparaison avec LaTeX.
