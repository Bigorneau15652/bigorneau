# Politique des scripts, du panneau de boutons et de la publication

## 1. Objet

Ce document consigne les décisions prises avec l'utilisateur sur trois sujets qui structurent la suite du plugin : un panneau de boutons à droite de la zone de rédaction, un mécanisme de scripts qui permet d'ajouter des fonctions sans alourdir le plugin de base, et la publication du plugin dans le répertoire communautaire d'Obsidian. Il complète docs/POLITIQUE-EXPORT.md, qui reste la référence pour le moteur d'export. Les règles de travail de la section 4.1 de ce document s'appliquent ici aussi : questions par petits groupes avec une recommandation, explications pas à pas pour toute manipulation sur GitHub, aucune dépendance ajoutée sans accord, aucun test désactivé.

## 2. Le panneau de boutons

L'utilisateur souhaite un panneau de petits boutons placé à droite de la zone de rédaction, au milieu de la hauteur de la page, disposés de haut en bas. Chaque fonction ajoutée au plugin reçoit un bouton et, en même temps, une commande de la palette de commandes, ce qui permet de lui attribuer un raccourci dans les réglages d'Obsidian. Le premier bouton porte l'icône du bigorneau, symbole du programme que l'utilisateur dessinera plus tard (une icône standard d'Obsidian la remplace en attendant). Il ouvre un menu qui permet d'ajouter des scripts et de rechercher de l'aide dans la documentation. Les autres boutons sont ceux des fonctions ajoutées, dans l'ordre d'ajout. L'utilisateur les déplace vers le haut ou vers le bas par un clic long suivi d'un glissement.

Pour réaliser cela, le plugin gardera un registre de fonctions. Une fonction est décrite par un identifiant, un nom en français et en anglais, une icône, une action et un texte d'aide. Le panneau et la palette de commandes lisent ce registre, et les scripts y enregistreront leurs fonctions. Les cinq commandes d'insertion de la version 0.1.7 (note de bas de page, table des matières, légende de tableau, formule en ligne, formule en bloc) en seront les premières entrées. Le panneau est prévu pour la version 0.1.9. Les questions sur son emplacement (tous les éditeurs de notes ou seulement les notes ouvertes avec la carte), sur la possibilité de masquer et de réordonner les boutons depuis les réglages, et sur la forme de l'aide restent à trancher avec l'utilisateur. Sauf avis contraire, le panneau est masqué par défaut sur tablette et téléphone, faute de place.

## 3. Les scripts

Un script est un fichier JavaScript que le plugin lit et exécute, comme le font les scripts du plugin Excalidraw. Le plugin lui fournit une interface qui permet d'ajouter une fonction (donc un bouton et une commande), de lire la note active, d'ajouter une langue, une police ou un style d'export. Un script peut en exiger un autre : le script Document long utilisera le script Formules pour dessiner les formules, et laissera sinon le texte tel qu'il est écrit. Chaque script déclare son nom et sa description en français et en anglais, la version de l'interface pour laquelle il est écrit et les scripts dont il dépend. Le plugin refuse proprement un script dont la version d'interface est incompatible.

L'utilisateur a choisi que les scripts soient rangés dans le dossier technique du plugin, invisible dans Obsidian, et non dans un dossier du coffre. Une fenêtre de gestion des scripts, ouverte depuis le bouton bigorneau, montre donc la liste des scripts installés, leur état et leurs versions. Les scripts viennent d'un catalogue officiel hébergé dans le dépôt GitHub du plugin : l'utilisateur clique sur « Installer » et le plugin copie le fichier dans le dossier technique, après avoir vérifié son empreinte. Rien n'est téléchargé sans ce clic. L'utilisateur peut aussi déposer un fichier à la main. Au premier lancement d'un script, le plugin demande une confirmation en montrant le nom, l'origine et la description du script, et mémorise la réponse. Un script dont l'empreinte a changé depuis la confirmation fait redemander l'accord. Un script a les mêmes pouvoirs que le plugin, c'est-à-dire qu'il peut lire et modifier toutes les notes et, sur ordinateur, accéder aux fichiers de la machine. La confirmation sert à ce que l'utilisateur le sache avant d'accepter.

Obsidian ne permet pas de retirer proprement une commande en cours d'usage. Quand l'utilisateur désactive un script, le plugin affiche donc un message qui précise que la désactivation ne prendra effet qu'au redémarrage d'Obsidian.

L'export actuel reste dans le plugin tant que le mécanisme de scripts n'est pas éprouvé. Il sera ensuite déplacé tel quel dans le script Document long, avec le même résultat et les mêmes tests, dans une version dédiée. Sans ce script, les entrées d'export du menu proposeront de l'installer. Les gabarits de documents (rapport, mémoire, ouvrage), prévus comme deuxième partie de la phase 7, deviendront des scripts de styles. Les scripts envisagés par l'utilisateur sont les suivants : Document long, qui donne accès aux autres ; la typographie française, la typographie anglaise britannique et la typographie anglaise américaine, chacune avec ses règles ; des polices et des styles d'export supplémentaires ; une sortie HTML ; Formules, pour composer facilement des formules complexes ; un script pour dessiner les tableaux plus facilement ; un script pour nommer les figures, les images et les tableaux. Ils seront réalisés l'un après l'autre. MathJax, qui pèse 2,6 Mo sur les 3,4 Mo du fichier du plugin, sera déplacé dans le script Formules, ce qui ramènera le plugin de base vers 0,8 Mo. Ces scripts officiels sont écrits en TypeScript dans ce dépôt, testés sans Obsidian comme le reste du moteur, puis assemblés en un fichier chacun.

L'installation du plugin par BRAT ne fournit que les fichiers main.js, manifest.json et styles.css de la release, donc les scripts officiels sont récupérés par le plugin lui-même depuis GitHub. Avant d'écrire cette partie, les règles du répertoire communautaire sur le téléchargement et l'exécution de code doivent être lues et respectées (section 4). Le mécanisme sera conçu à partir de ce que ces règles autorisent.

## 4. Publication dans le répertoire communautaire d'Obsidian

L'utilisateur souhaite publier le plugin prochainement. La procédure ci-dessous est tirée de la documentation officielle des développeurs (pages Submit your plugin et Plugin guidelines du dépôt obsidianmd/obsidian-developer-docs, lues le 2 octobre 2026). Les pages Developer policies et Submission requirements for plugins n'ont pas pu être lues depuis l'environnement de développement : leurs règles restent à vérifier.

Le dépôt doit contenir à sa racine un fichier README.md qui décrit le but du plugin et son usage, un fichier LICENSE qui fixe les droits d'usage du plugin et de son code source, et un fichier manifest.json. Il faut ensuite créer sur GitHub une release dont l'étiquette est identique à la version du manifest (trois nombres séparés par des points) et y joindre main.js, manifest.json et styles.css. La soumission se fait sur le site community.obsidian.md : connexion avec un compte Obsidian, liaison du compte GitHub pour prouver que le dépôt appartient au soumissionnaire, puis ajout du plugin. Le répertoire lit le manifest.json à la tête de la branche principale, et l'identifiant du plugin doit être unique et ne pas contenir le mot obsidian. Une revue automatique indique ce qui est à corriger ; les corrections se font dans le dépôt, avec une nouvelle release à la version augmentée. Après publication, l'annonce se fait dans le forum Share & showcase et sur le canal #updates du Discord.

L'état du dépôt au 2 octobre 2026 est le suivant. Le fichier LICENSE est absent. Le README.md est une liste continue rédigée pour le suivi du projet et doit être réécrit pour des lecteurs qui découvrent le plugin, avec des captures d'écran. La description du manifest est en français sans accents et doit être rédigée en anglais. Le code contient dix expressions régulières avec « lookbehind » (dans les fichiers typography.ts, insert.ts, math.ts et inline.ts du dossier src/export) : à ma connaissance, les iPhone et iPad antérieurs à iOS 16.4 ne les acceptent pas et le plugin entier ne se chargerait pas sur ces appareils, ce qui justifie de les réécrire. Le code contient seize usages de innerHTML pour des icônes dont le texte est fixé dans le programme : les consignes officielles demandent de les remplacer par la construction d'éléments avec l'interface d'Obsidian. Il contient aussi cent quarante et une affectations de styles en ligne, à trier entre celles qui sont des positions calculées (acceptables) et celles qui fixent des couleurs ou des polices (à déplacer dans styles.css). Les points suivants sont conformes : pas de journal inutile dans la console, pas de raccourci clavier par défaut, commandes avec le bon type de rappel, pas de télémétrie, aucun accès au réseau pour l'instant. Le catalogue de scripts introduira un accès au réseau, qui devra être déclaré dans le README.

## 5. Ordre des travaux

La version 0.1.8 prépare la publication : licence, README en anglais et en français, description du manifest, expressions régulières, innerHTML, styles en ligne, vérification des règles du répertoire. La version 0.1.9 apporte le panneau de boutons et le registre de fonctions. La version 0.2.0 apporte le mécanisme de scripts, après vérification des règles sur le code téléchargé. Viennent ensuite le déplacement de l'export dans le script Document long, puis les autres scripts un par un, puis la phase 8 de comparaison avec LaTeX.
